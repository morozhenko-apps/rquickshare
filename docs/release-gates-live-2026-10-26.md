### Protected release publication sequence (do not execute without explicit approval)

1. Finalize/current-code installed Pixel/KDE and failure matrix with rollback and measured evidence. Resolve blockers or explicitly restrict supported scenarios and obtain applicable risk decisions.
2. Produce final non-debug native product `0.9.0-1`, verify Cargo/lock/revision and package metadata/ABI, source SHA, hashes, install/migration/removal. Ensure no unaccepted source drift.
3. Verify **effective** `master` rulesets and `native/v*` tag protection + protected `apt-release` environment and secret presence. GitHub `master.protected=true` alone is insufficient proof.
4. Complete tagged 10× MODE B and release contract CI. After review, promote verified `dev` → protected `master`, create exactly one immutable annotated **`native/v0.9.0`** tag matching HEAD; never retag historical upstream `v0.9.0`.
5. CI signs/publishes one immutable versioned `.deb`, signed APT `InRelease` and R2 objects; verify independent `Signed-By` APT install, direct HTTPS checksums, rollback/refresh, then publish GitHub Release. No unauthenticated manual R2 writes.
