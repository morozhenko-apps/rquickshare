# Native GTK transient peer session, no phantom empty transfer

Date: 2026-10-24. Issue [#22](https://github.com/morozhenko-apps/rquickshare/issues/22). User confirmed all 3 Pixel declines after restart and 6/6 across two daemon lifetimes, but reports slow first discovery and a compact card saying `Transfer · 0 files · Cancel` while `Visible to nearby devices · 0:12`. These are different workstreams: misleading GTK status vs discovery time.

## Root-cause protocol interpretation / invariants

`core_lib/src/sessions/details.rs::TransferDetails::default`: `status=Unavailable`, `kind=Files`, `files=[]`. This is an intentionally safe placeholder until the real, authenticated payload metadata arrives. It does **not** imply the user sent an empty file list. `native_desktop/src/panel/rows.rs::payload_label` currently formats an empty Files vector as `0 files` without consulting `status`. The row uses an empty sender fallback `Transfer`, and `card_transfer_visible` intentionally includes unbound nonterminal sessions so users can cancel a real stalled handshake. Thus hiding the session would destroy a useful intervention control and mask the next discovery failure.

**Selected narrow UI-only design:** For `DetailsStatus::Unavailable`, render a neutral `Waiting for details` summary; for `Unsupported`, `Unsupported content`. For `Ready`, keep existing format inference and file/text/link labels. When both recipient and sender are unknown and metadata is unavailable, use `Connecting…` as the peer title; when a real source name is known preserve it. Keep legitimate `Cancel` control, native event ownership, real transfer ID, Phase, source revision/metadata transition, visibility, history and storage unchanged. Never infer identity from the name and never claim bytes/files exist while Unavailable. Add pure helper tests for all three statuses, ready single/multiple file, ready text/link, supplied sender and fallback. Add a GTK widget assertion that premetadata row has the neutral label without sacrificing Cancel. Root file `native_desktop/src/panel/rows.rs`, no Core changes.

Alternative fixes rejected: deleting early `Active` session rows (hides cancellation and masks stuck peer), manufacturing an anonymous file (lies to user), changing daemon `Phase` based on GTK presentation (couples UI to protocol), joining transfers by name (violates #16). No new UI performance timer or mechanical change to discovery.

## Cold detection independent, need evidence first

Issue [#18](https://github.com/morozhenko-apps/rquickshare/issues/18) retains cold-start uncertainty. The existing **opt-in** `RQUICKSHARE_RECEIVER_TRACE=1` emits fixed monotonic milestones: `runtime_start_requested`, `runtime_core_ready`, `runtime_discovery_worker_ready`, `mdns_browse_started`, `first_mdns_route_admitted`, `visible`, `advertisement_started`, `gatt_slot0_read` and `gatt_header_ready`. Request the *full allowlisted sequence for one genuinely new daemon process* with user-reported time from activating Pixel discovery to first PC row; previous `reject_*` grep suppressed all discovery markers, so one cannot diagnose root cause from those older logs. An `elapsed_ms` number is relative to the daemon's first trace event, not the phone's first scan. The 0:12 screenshot is remaining visibility duration, not a discovery measurement. Compare startup/core delay, browse admission, BLE advert activation and first Google GATT read before any architectural optimization; do not tune network timeouts/retries without a trace.
