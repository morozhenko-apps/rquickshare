## Peer identity architectural STOP FACTOR (not implemented in this task)

Required invariant: a display name (or mDNS fullname/IP/Bluetooth MAC alone) **must never confer durable identity, automatic trust, accepted consent, or redirect a chosen send**. A unverified duplicate remains a separate selectable route rather than being silently collapsed into an arbitrary route. An accepted inbound, authenticated proof and outbound discovery association may link only when actually cryptographically justified; preserve route-local endpoint selection and generation/restart revocation. Core API/endpoint association and possibly trust boundary change is material and must not be guessed.

Architectural alternatives for owner decision:
- **A — Strict verified association (recommended).** Keep all unproven endpoints as distinct sendable entries; after authenticated session identity/cryptographic binding to a currently advertised route, display one device card containing all proved inbound/outbound route aliases; maintain per-route actual address/transport, preserve exact explicit selection, no remembered identity or auto-accept. **Pros:** prevents mistaken merges and spoofing, works without accounts, inherits live authentication. **Cons:** unknown duplicated mDNS ads remain visible until verified; requires binding proof across session/discovery and possibly additive daemon snapshot API. **Risks:** proof/generation races; fail closed on ambiguous paths.
- **B — Presentation grouping of unverified candidates.** Group apparent aliases into a visually marked *unverified group* with separate explicit child routes, never one automatic Send target and never implied verification. **Pros:** less visual clutter before handshake, no new trust authority. **Cons:** still requires an extra route choice; doesn't prove physical sameness and could conceal multiple distinct users if expanded incorrectly. **Risks:** confusing labels and misinterpreted groups; no silent sending permitted.
- **C — Persistent user-approved link registry.** Ask user to affirm that two endpoints represent the same local device, persist the mapping and expire/reauthenticate before sending. **Pros:** consistent later display after opt-in. **Cons:** new persisted trust-like model, migration/recovery, deliberate risk of relinking wrong devices; can diverge from ephemeral Google identity. **Risks:** dangerous stale aliases; separate consent/identity acceptance remains mandatory.

Recommendation **A**, since requested objective is one real device with reliable identity and safe sending, not merely a shorter list. **STOP:** no production identity merge or new authenticated binding API until owner chooses A/B/C. UI focus, cold-start diagnostics, docs and localization planning are independent.
