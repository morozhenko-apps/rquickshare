## Four independent identity concepts

1. **Transport address:** IP, port, BT MAC, BLE peripheral; sufficient ONLY to address a particular transport, never to say two advertised routes share a human/device identity.
2. **Protocol endpoint ID (4 bytes):** short-lived, broadcast, attacker-controlled untrusted correlation hint across observed mediums of a single advertising generation. The Google open-source library *does* use one local endpoint ID across advertisements in a generation. For visual tentative candidate grouping, may be sufficient **if the owner approves a change from A** and every exact selectable route remains distinct. Four bytes alone cannot authorize unattended route selection or trust.
3. **Authenticated session/UKEY2 PIN:** cryptographically binds current handshake and keys; user can compare PIN for *this connection*. A successful transfer does not prove that other separate discovery advertisements share that particular authenticated connection.
4. **Credential-backed peer plus proved exact route:** `VerifiedPeerCredential` from trusted certificate+PairedKey `Success` is a foundation. Must further bind the selected advertised route to this same live authenticated peer and epoch before asserting one **verified device**. A Google account's own-device/contacts association cannot be fabricated from random TXT certificate-metadata bytes.

## MODE A staged design / accepted safety invariants

### Stage 1 — safe, non-behavior-changing decoding (approved as routine parsing)

Introduce a pure `parse_mdns_endpoint_id` helper using the existing base64url `gen_mdns_name` inverse; require exact 10-byte layout, PCP 0x23, service hash 0xFC9F5E, trailing 0x0000 and exactly four alphanumeric ASCII endpoint bytes. Decode **only** the first instance label of a well-formed `._FC9F5ED42C8A._tcp.local.` fullname; no acceptance of differently typed services/extra labels/embedded separators/padded base64/malformed UTF-8/control chars. Its output is an **UnverifiedEndpointHint** with Debug redaction; never elevate to `VerifiedPeerCredential`, affect `NativeRuntime::send_selection` or outbound address, consent, persistence, runtime schema or session trust. Unit tests: generated roundtrip, unrelated services, zero/too-long IDs, mutated fixed markers, malformed encoding, same-name/different-hint, same-hint/different-services, expiry/churn fixture, alias redaction.

### Correct binding, automatic transport, and fail-closed ambiguity

1. **Identity admission and contradictions:** A candidate group must have positive evidence of common device/advertising generation, with no conflicting available name, type, separately verified peer key, endpoint generation, advertisements' exact ID, session claim, or current network route metadata. An ephemeral 4-byte Nearby ID is a **hint**, not sufficient by itself, and the absence of a contradictory field is **not positive proof**. Multiple currently valid links must be bound to the same verified/correlated peer under a documented evidence policy. If evidence is missing, ambiguous, contradictory or stale, **keep independent device entries with the existing unchanged appearance**.
2. **Transport choice is AUTOMATIC, not a user action.** When multiple currently live eligible transport candidates legitimately belong to the same accepted device, Core selects one **best available route** using observed reachability, suitability and measured connection performance (do not use advertised names, a fixed “Wi-Fi always wins”, presumed throughput, or unmeasured RSSI as absolute proof). Prefer fast successful TCP/Wi-Fi data transport when actually available and authenticated; otherwise the working secure fallback. Preserve Google-compatible in-session BLE→TCP BWU; do not invent new wire behavior. A tie uses a stable deterministic order, never parallel sends.
3. **Exactly one recipient and one logical outbound session:** selecting a device never multicasts initial request/PIN/consent/file payload to all routes. Choose one current exact endpoint and establish one peer handshake/consent, with no other route contacted as part of the same transfer. Duplicate ephemeral hints on two real devices must never trigger duplicate notifications.
4. **No unsafe auto-failover:** a broken candidate may be replaced only **before** starting a peer-visible consent or payload exchange, after verifying that the replacement independently belongs to the same allowed device and its route is still valid. After consent, transmission starts, a peer Reject, Cancel, or transport-close, there is **no silent second-device retry**; a same authenticated in-session BWU is an explicit transport migration, not a new recipient.
5. **Lifecycle/identity:** route ranking and correlation expire on tombstone, epoch change, device restart, certificate revocation/key rotation, conflicting new advertisement or lost discovery. Never persist guessed device ties or infer them from a display name, IP, BLE MAC, 4-byte ID alone or Google account claim in plaintext. #8 BWU plaintext route-consumption risk stays separately unresolved.
6. **UI contract:** continue rendering the *existing* device list, unchanged CSS/widgets/window dimensions/buttons/icons, with fewer entries **only when backend identity correlation is established**. If not, show two existing rows, without warnings, route pickers or special statuses. UI receives one logical selectable device ID (when grouped) and no transport selection control.
7. **Implementation status:** this is now the approved #16 policy, NOT yet implemented end-to-end. Today rQuickShare's native outbound discovery yields only mDNS routes, and its active Pixel PairedKey flows are anonymous. There is no authentic Bluetooth-outbound route list, verified certificate provider, live route quality telemetry or accepted cross-transport binding. Therefore *do not fake a best route choice or claim verified grouping*. Current Send code already creates one transport job per explicit endpoint; its invariant is reinforced by a new test against conflicting short-lived hints. Build the identity/correlation registry and real medium adapters before calling this feature done.

### Revised regression oracle

- R1: one peer, two evidence-linked eligible routes, choose highest measured quality automatically; one request, one consent, one actual payload stream, no fanout; repeat deterministically.
- R2: two unrelated peers share display name and 4-byte endpoint ID, but show conflicting key/type/route-generation/name/IP-origin data → **two unchanged entries**, never choose between them invisibly.
- R3: same endpoint ID with missing additional positive evidence → **two unchanged entries**, not auto-merged.
- R4: same real peer, Wi-Fi fails admission before any contact, authenticated BLE remains eligible → fall back automatically to **that same peer** only, no duplicate consent.
- R5: peer rejected or sender canceled after initial contact → stop; do not try second route/device.
- R6: tombstone/restart/epoch/revocation/expired peer proof during ranking → remove aliases/recompute without stale route or persistent identity.
- R7: identical route quality → deterministic single endpoint; no race between duplicate job submissions.
- R8: UI layout snapshot, visible labels, focus/buttons/card count on ambiguous ads → existing controls and appearance unchanged.
- R9: concurrent transfers/consent with same hint collision → independent token, files, recipient and terminal state.
- R10: malformed/stale/mismatched trusted route proof → no merge, no quality-based override, no Send misdirection.
- R11: BLE→TCP BWU under active session follows authenticated session ownership, not fresh device selection or multicast.
- R12: Windows Native and Linux KDE share the same Core route policy; platform-specific availability measurements vary, consent/identity invariant remains identical.

**Current automated evidence:** native Core already keeps separately discovered fullnames and sends to one exact route. A focused runtime source test added in commit `0d9026f` checks same short-lived ID with contradictory name/address remains separate and emits one job to only the intended address. No real multi-route auto-ranking claimed until actual inputs/binding are present.

## 2026-10-26 next source slice: address-generation-safe routing and measured availability

After explicit owner confirmation, **no new layout, manual transport picker, icon, or grouped-row UI was added**. Native still has only one outgoing mDNS discovery provider; it cannot infer cryptographically verified BLE/mDNS dual transport, so full automatic best-of-media ranking remains OPEN.

Production change `core_lib/src/service/runtime.rs` (code `fe525fcc`): an mDNS update reusing the **same untrusted service fullname** but replacing IP or port no longer preserves its old exact-recipient endpoint capability. It atomically removes the old endpoint and registers a fresh per-epoch/sequence route ID under one Coordinator snapshot update; unchanged address/name remains a no-op, rename alone retains route identity. This protects against one same-fullname address takeover while a file is queued, pending under backpressure, or already in flight. The transfer that selected the former route fails instead of silently being sent to a new, unverified socket; an already established transfer owns its original socket. Change does not silently auto-retry on another peer, send multiple notifications, or grant same-device identity based on IP/fullname.

Source tests (commits `fe33b0f3`, `eebaa58c`, `edc3cca8`) update all prior old-route assumptions and exercise:
- Same name, changed port or IP → distinct route capability, old route retired; label-only change → same capability.
- Queued and backpressure-delayed Send → old selected transfer fails without any outbound job to the new socket, no reservation leak.
- Active Send job → remains attached to its original endpoint, despite discovery of a replacement; no second job.
- Existing same-hint two-recipient test `aec465bf` now uses distinct dedup tokens, exercising ReplayConflict correctly rather than suppressing it.
- [New asynchronous mDNS probe regression](../core_lib/src/hdl/mdns_discovery/probe_tests.rs) `cbc6cff3`: when one service has multiple advertised IP addresses, whichever actual TCP connect succeeds *first* becomes the only published live route. The slower still-pending probe is canceled. This is an actual current automatic working-address choice; it does **not** measure payload bandwidth, nor prove two independent BLE and LAN advertisements come from the same person/device.

Security note: changing IP/port under the same mDNS instance may be normal Wi-Fi address churn, not necessarily an attacker. Until a cryptographically valid binding is available, failing already queued work is preferable to redirecting to an unverified different address. A fresh user-initiated Send after this update can use the newly measured reachable route from the unchanged device list. Do not call this finished #16 automatic cross-media ranking, and do not imply an unverified ephemeral endpoint hint proves a Google account.
