## Four independent identity concepts

1. **Transport address:** IP, port, BT MAC, BLE peripheral; sufficient ONLY to address a particular transport, never to say two advertised routes share a human/device identity.
2. **Protocol endpoint ID (4 bytes):** short-lived, broadcast, attacker-controlled untrusted correlation hint across observed mediums of a single advertising generation. The Google open-source library *does* use one local endpoint ID across advertisements in a generation. For visual tentative candidate grouping, may be sufficient **if the owner approves a change from A** and every exact selectable route remains distinct. Four bytes alone cannot authorize unattended route selection or trust.
3. **Authenticated session/UKEY2 PIN:** cryptographically binds current handshake and keys; user can compare PIN for *this connection*. A successful transfer does not prove that other separate discovery advertisements share that particular authenticated connection.
4. **Credential-backed peer plus proved exact route:** `VerifiedPeerCredential` from trusted certificate+PairedKey `Success` is a foundation. Must further bind the selected advertised route to this same live authenticated peer and epoch before asserting one **verified device**. A Google account's own-device/contacts association cannot be fabricated from random TXT certificate-metadata bytes.

## MODE A staged design / accepted safety invariants

### Stage 1 — safe, non-behavior-changing decoding (approved as routine parsing)

Introduce a pure `parse_mdns_endpoint_id` helper using the existing base64url `gen_mdns_name` inverse; require exact 10-byte layout, PCP 0x23, service hash 0xFC9F5E, trailing 0x0000 and exactly four alphanumeric ASCII endpoint bytes. Decode **only** the first instance label of a well-formed `._FC9F5ED42C8A._tcp.local.` fullname; no acceptance of differently typed services/extra labels/embedded separators/padded base64/malformed UTF-8/control chars. Its output is an **UnverifiedEndpointHint** with Debug redaction; never elevate to `VerifiedPeerCredential`, affect `NativeRuntime::send_selection` or outbound address, consent, persistence, runtime schema or session trust. Unit tests: generated roundtrip, unrelated services, zero/too-long IDs, mutated fixed markers, malformed encoding, same-name/different-hint, same-hint/different-services, expiry/churn fixture, alias redaction.

### Stage 2 — possible but **architectural STOP FACTOR** pending user selection

**A. Keep current verified-only grouping (existing approval).** Expose hints solely for diagnostics; multiple unverified routes remain separate. Best security semantics, no improvement to repeated unverified rows until real certificates/binding.

**B. Provisional presentation-only grouping (potential user-requested adjustment).** Show one visually **Unverified / Possible same device** group when same generation and exact 4-byte Google endpoint ID (optionally compatible advertised type) recur. Always expose every individual route with its current exact `ep-*` recipient handle; user must select route explicitly, never inferred and never auto-switch on failing first route. Do not attach incoming transfer/consent automatically to an unverified group, store durable associations, elevate to trusted, or expose spoof-sensitive account claims. A spoofed same ID can only create a confusing cosmetic collision, not redirect Send silently. Invalidate on tombstone, loss of discovery, different generation/restart, conflicting IDs/metadata, stale endpoint, or limit overflow. Pros: fewer visible duplicate headings with clear route choices, matches known protocol hint behavior. Cons: extra route selection, spoof-induced UI grouping, UX/security wording and additive snapshot/view contract need explicit design and acceptance. **Recommended if owner wants Android-like cleaner discovery before credential support**, conditional on exact-route proof not being claimed.

**C. Group after one manually verified secure connection, but no certificate-backed identity.** Only bind the exact route selected and confirmed for that connection, not arbitrary same ID sibling routes; a separate challenge/ownership proof still required to confidently include siblings. Promoting a PIN match to durable or unrelated sibling identity would be unsound. Pros: trust limited to live session. Cons: does not solve pre-connection duplicate list without another ownership handshake; cannot close full #16 alone.

The user previously selected **A for #16**. Switching to **B** changes the trust/presentation contract, even if routing remains fail-closed; it is not silently authorized by a request to *investigate* whether lower-confidence evidence might be sufficient. Only stage 1 may proceed without a new approval.

### Stage 3 — real authenticated-grouping work (still blocked by concrete trust prerequisites)

Legitimate provider of peer certificates/Google-compatible signed identity, secure renewal/revocation, actual route-to-session ownership proof, no unproved cross-transport alias, corresponding runtime and GTK presentation projection, privacy constraints, MODE B matrices, Android/Windows physical acceptance. Keep issue #16 open until those gates are met; do not claim Google Windows app source behavior from its closed binary.

## Verification plan

Lightweight format/static safety diagnostics during implementation; at final code stage run stable+flaky independently, no CI polling. Tests must reject four-byte collisions from being identity, parse malformed or adversarial fullnames, ensure no route redirect, no trust/consent bypass, no persistence and no phantom regroup after restart. The newly written decoder is only **data recognition** and does NOT warrant % coverage, release acceptance, Android peer grouping or any Windows-support claim.
