# Native device identity: cryptographic route-binding audit and implementation gates

Date: 2026-10-24. Issue [#16](https://github.com/morozhenko-apps/rquickshare/issues/16). Owner has approved **Option A**: collapse device aliases only after cryptographically verified, session-bound identity proof. This document records the remaining **source-proven preconditions**, not a fabricated trust link. No executable or wire changes in this audit.

## Source evidence (reviewed against dev)

| Code | Observed semantics | Consequence |
| --- | --- | --- |
| `core_lib/src/peer_authentication.rs::PeerAuthentication` | Implements token-bound ECDSA P-256 signature verification against a supplied peer `CertificateMaterial.public_key`, local shared-key hash matching and `Outcome::{Success,Unable,Fail}` folding. The certificate source is injectable in unit tests; a `CertificateSource` supplies current certificate materials. | Crypto verifier exists, but verifier alone does not establish peer identity or a route link. |
| `PeerAuthentication::anonymous` | Uses `AnonymousSource`; its `snapshot()` returns empty credentials. `verify` without peer certificate yields `Unable` rather than verified signature success; `finish()` accepts `Unable` for compatibility unless there is a hard `Fail`. | A successful transfer may still be **anonymous**; `Ok(Outcome::Unable)` must never produce a verified-device identity. |
| `core_lib/src/hdl/{inbound,outbound}.rs` | Both request constructors currently instantiate `PeerAuthentication::anonymous(Role::{Receiver,Sender})`. Their paired-key handlers call `verify` and `finish`, but `finish` result is not saved as a stable verified identity in the runtime. | The default Native path has no credential-backed peer certificate identity to export or join to discovery. |
| `core_lib/src/hdl/mdns_discovery.rs::MDnsDiscovery` | Exposes `EndpointInfo` `fullname`, `id` formatted as IP:port, name, IP, port and advertised type after TXT parsing and TCP reachability. | Reachability and metadata are **not authenticated proof** of physical/device identity; spoofable route hints cannot become a trust anchor. |
| `core_lib/src/service/runtime.rs::discovered` | Stores one ephemeral route per service fullname; generates per-epoch `ep-...` IDs. Updates/removes a route only by matching current fullname. | One route card per announcement is currently correct fail-closed behavior until proof exists. |
| `NativeRuntime::observed(SessionEvent)` | Owns inbound sessions by session ID and transfers via capability-bearing `SessionControl`, but has no field linking a cryptographically verified certificate to an extant mDNS route. | No safe inference that an inbound request and a displayed outbound route are the same authenticated peer. |
| `core_lib/src/manager.rs` BWU classifier | Selects a pending BWU socket using plaintext `CLIENT_INTRODUCTION` endpoint / previous-endpoint identifiers before consuming route; issue #8 tracks absence of pre-consumption authenticated owner proof. | Do not use BWU alias as an identity proof or build grouping atop it. #8 may block secure cross-transport route claiming. |

## Explicit threat model / invariant map

- An attacker may advertise the same display name, hostname, service fullname, IP/port after network churn or a previously observed BLE endpoint ID. None of these values can cause verified grouping, Send recipient re-selection, consent re-use or cross-session trust.
- Distinct verified public keys, stale certificates, failed/unavailable key sources, `Outcome::Unable`, partial signed-data results or expired credentials must fail closed to **unlinked** route cards; peer signature verification is not equivalent to route linkage until an exact connection or authenticated proof binds the advertised route and live session.
- A `VerifiedPeerId` must derive from validated credential identity (not an arbitrary name or `proof_digest`, which hashes **the packet fields** and does not by itself prove a signer) and be scoped to current session generation, proof validity and certificate/key lifetime. Never expose raw certificates, private/shared secrets, key material, addresses or peer names in diagnostic logs.
- Bind `VerifiedPeerId` to an **exact route and the established authenticated secure session**, plus epoch/expiry, only when a security-reviewed verification path supplies the proof. Preserve each independently addressable transport route even when GTK eventually visually groups multiple routes; an ambiguous choice must still require an explicit recipient route.
- Revocation/removal, session expiry, daemon restart, mDNS tombstone, reused fullname, stale proof replay, authentication `Unable` or differing fingerprints must invalidate links. Unknown remains unknown rather than guessed group. Consent decisions stay per live transfer/revision.

## MODE A plan: distinct dependent stages (NOT implemented)

1. **Certificate source and trust lifecycle**: decide how a real verified peer certificate is obtained, stored, refreshed and revoked on Linux and how its legitimacy relates to Android Google Quick Share. Existing `AnonymousSource` supports transfer interoperability but has no credential identity. No synthetic permanent ID, local name/IP cache or hard-coded public key can replace this. New persistence/key-management authority requires a separate security review.
2. **Proof-result contract**: define an internal narrowly scoped verified-auth result carrying only stable verified certificate-derived handle plus live session/role/epoch metadata. Export it from `PeerAuthentication::finish` **only for `Outcome::Success` with actual peer signature verification**, not merely success-shaped remote wire status or local hash equality. Match token/role and current time; reject replay, mismatch, `Unable` and degraded source. No UI visibility of secrets.
3. **Exact authenticated route association**: prove that the mDNS/BLE endpoint identified at selection corresponds to that authenticated session (not just that some independently accepted connection proved a key). This is **not currently available** from the SDK-discovery announcement and requires a protocol/security architecture choice. Do not implement automatic connection or modify BWU packet layout as a shortcut. Coordinate with pre-consumption BWU owner proof (#8).
4. **Runtime/UI projection**: store revocable, ephemeral `verified group` metadata and distinct route IDs in serial `NativeRuntime`, exposing a separate view type rather than replacing the actual route keys. GTK can group only currently proven routes; unverified advertisements stay separate. Failed or ambiguous binding must never alter Send address or consent capabilities.
5. **Verification**: deterministic fake key source with real ECDSA fixture; 0/1/128 routes; same names vs distinct keys; rotated/revoked/expired keys; cross-epoch/replayed/stripped proof; inbound/outbound and BLE/mDNS/BWU races; route lost/readded, consent rejection/cancel, and Tauri/native GTK snapshots. Final-source Mode B gate, Android/Windows real peers and privacy audit remain distinct.

## Decision/dependency gates

The owner already selected A (verified only), so there is **no need** to ask to repeat A/B/C. However, the **source of trustworthy peer certificates** and the **on-wire/existing-session proof that binds a certificate to a specific advertised route** are separate unresolved security/API choices; they cannot be inferred or silently invented by the agent. Therefore, do not write a fake 'verified' identity or merge any current anonymous routes.

This audit does **not** close #16, does not authorize unauthenticated grouping, and does not substitute for #8 ingress proof. No executable changes, package changes, master promotion or CI run are associated with this document. The 20-language #17 step remains the last functionality gate before global 1.0.0 testing.
